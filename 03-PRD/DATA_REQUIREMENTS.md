# Urimai Kaavalan — Data Requirements

> **Phase:** 1 — PRD & Acceptance Criteria
> **Source:** 03-PRD/01_URIMAI_KAAVALAN_GOVERNMENT_PRD.pdf (§19 — Data Model; §21 — Security & Privacy)

---

## Core Data Domains

*(Source: PRD §19)*

### 1. Identity Domain

| Entity | Key Attributes | Notes |
|---|---|---|
| `users` | id, role, name (encrypted), contact (encrypted), status, created_at, last_login | All PII encrypted at field level |
| `roles` | id, role_name, permissions_json | RBAC role definition |
| `permissions` | id, resource, action, role_id | Least-privilege grants |
| `families` | id, user_id, primary_contact (encrypted), language_preference | Family group record |
| `prisoners` | id, name (encrypted), dob (encrypted), case_id | Accused person — not public |

**Privacy note:** Prisoner records are sensitive. Access restricted to assigned PLV, lawyer, DLSA officer, and system admin only.

---

### 2. Case Domain

| Entity | Key Attributes | Notes |
|---|---|---|
| `cases` | id, family_id, platform_case_id, fir_number, police_station, district, status, created_at, updated_at | Central case record |
| `case_events` | id, case_id, event_type, actor_role, actor_id, timestamp, source, metadata_json | Immutable event log |
| `case_statuses` | id, case_id, status, changed_at, changed_by_role | Status history |
| `case_priorities` | id, case_id, priority_level, priority_reason, set_by_role, set_at | Priority escalation |

**Case Status Enum** (from PRD §10):
`NEW | INTAKE_INCOMPLETE | UNDER_REVIEW | LEGAL_AID_REQUESTED | LAWYER_ASSIGNED | ACTION_REQUIRED | HEARING_SCHEDULED | RESOLVED | ESCALATED`

**Business Rules:**
- `case_events` is append-only — no updates or deletes.
- `platform_case_id` is generated by the system — distinct from judicial CNR.
- `fir_number` is nullable (intake may be incomplete).

---

### 3. Documents Domain

| Entity | Key Attributes | Notes |
|---|---|---|
| `documents` | id, case_id, document_type, storage_key (encrypted), file_hash, upload_by_role, upload_at, scan_status | File reference only — no file contents in DB |
| `document_pages` | id, document_id, page_number, ocr_raw_text (encrypted), ocr_confidence | Per-page OCR output |
| `document_extractions` | id, document_id, field_name, extracted_value (encrypted), confidence, source_page, verified, verified_by_role, verified_at, corrected_value (encrypted) | Per-field extraction with verification |

**Storage Note:** Actual file content is stored in private object storage (not the database). `storage_key` is a reference to the storage location, encrypted in the database.

**Business Rules:**
- `scan_status` must be `CLEAN` before `document_pages` or `document_extractions` are created.
- `extracted_value` is never automatically trusted — `verified = false` until PLV/user confirms.
- `corrected_value` stores the human-corrected value when different from OCR.

---

### 4. Legal Knowledge Domain

| Entity | Key Attributes | Notes |
|---|---|---|
| `legal_sources` | id, title, law_name, source_url, version, effective_date, review_status, reviewer_id, approved_at | Source registry |
| `legal_source_chunks` | id, source_id, chunk_text, chunk_index, embedding_vector | For RAG retrieval |
| `legal_rules` | id, title, rule_category, description, created_by_role, review_status | Rule definition |
| `legal_rule_versions` | id, rule_id, version_number, rule_logic_ref, effective_date, deprecated_at, approved_by, approved_at | Versioned rule |
| `legal_citations` | id, source_id, section_ref, citation_text, generated_at, validated | Per-response citation |

**Business Rules:**
- `legal_sources` with `review_status = PENDING` must NOT be available to the RAG pipeline.
- `legal_rule_versions` must record effective_date — rules activate on effective_date, not approval_date.
- `legal_citations.validated = false` means citation has not passed validation check; must not be shown to user.

---

### 5. AI / Eligibility Domain

| Entity | Key Attributes | Notes |
|---|---|---|
| `eligibility_checks` | id, case_id, rule_version_id, triggered_at, triggered_by_role | When a screening was run |
| `eligibility_results` | id, check_id, signal, confidence_band, facts_detected_json, facts_missing_json, rule_source_id | Output of screening |
| `model_versions` | id, model_type, version_tag, deployed_at, deprecated_at | AI model version tracking |
| `model_evaluations` | id, model_version_id, eval_dataset_id, accuracy, precision, recall, hallucination_rate, evaluated_at | Performance metrics |
| `bias_audits` | id, model_version_id, dimension, group_label, metric_name, metric_value, audit_date | Disaggregated bias metrics |

**Business Rules:**
- `signal` enum: `POTENTIAL_CRITERIA_IDENTIFIED | NO_CRITERIA_IDENTIFIED | INSUFFICIENT_INFORMATION`
- `confidence_band` enum: `HIGH | MEDIUM | LOW`
- `bias_audits` must be run before any ML model is deployed at scale.
- `model_evaluations` is a prerequisite for any ML layer — rule-based engine does not require ML evaluation.

---

### 6. Legal Aid Domain

| Entity | Key Attributes | Notes |
|---|---|---|
| `lawyers` | id, bar_number (encrypted), name (encrypted), dlsa_district_id, verified, verification_date, status | Professional registry |
| `lawyer_languages` | id, lawyer_id, language_code, proficiency_level | Language matching |
| `lawyer_specializations` | id, lawyer_id, case_category | Offence-type specialization |
| `legal_aid_requests` | id, case_id, family_id, request_date, status, language_preference, nature_of_request | Aid application |
| `lawyer_assignments` | id, request_id, lawyer_id, assigned_by_role, assigned_at, confirmed_at | Assignment record |
| `sla_records` | id, assignment_id, sla_deadline, breached, breach_notified_at | SLA tracking |

**Business Rules:**
- `lawyers.verified = false` must never appear in matching results shown to DLSA.
- `sla_records.sla_deadline` is computed from the district's SLA policy — not a hardcoded value.
- A `legal_aid_request` in `ASSIGNED` status must have exactly one active `lawyer_assignment`.

---

### 7. Operations Domain

| Entity | Key Attributes | Notes |
|---|---|---|
| `notifications` | id, case_id, recipient_id, notification_type, channel, content_i18n_key, status, sent_at, delivered_at | All notification records |
| `voice_sessions` | id, caller_id_hash (not full number), session_start, session_end, language, flow_path, outcome, audit_ref | IVR session log |
| `prison_confirmations` | id, case_id, query_type, requested_by_role, requested_at, responding_facility_id, result, responded_at | Confirmation audit |
| `human_reviews` | id, eligibility_check_id, reviewer_role, decision, override_reason, reviewed_at | Human review of AI |
| `human_overrides` | id, human_review_id, original_signal, override_signal, reason_category, reason_text | Override detail |
| `audit_logs` | id, actor_id, actor_role, action, resource_type, resource_id, ip_hash, timestamp, metadata_json | Immutable security audit |

**Business Rules:**
- `audit_logs` is append-only — no updates or deletes by any role.
- `voice_sessions.caller_id_hash` stores a one-way hash of the caller ID — not the raw phone number.
- `human_reviews.decision` enum: `AGREE | OVERRIDE`.
- `human_overrides.reason_text` is mandatory — cannot be null.
- `prison_confirmations.result` enum: `CONFIRMED | DENIED | UNABLE_TO_CONFIRM`.

---

### 8. Integration Domain

| Entity | Key Attributes | Notes |
|---|---|---|
| `organizations` | id, name, type, district_id | Government / legal-aid orgs |
| `districts` | id, name, state, sla_policy_json | District configuration |
| `police_stations` | id, name, district_id, station_code | Reference data |
| `courts` | id, name, district_id, court_type | Reference data |
| `prisons` | id, name, district_id, capacity | Reference data |
| `integration_records` | id, connector_type, request_payload_hash, response_status, attempted_at, error_detail | Adapter layer audit |

**Business Rules:**
- `integration_records.error_detail` must be logged when any connector returns an error.
- Failed integrations must not silently update case records.
- `police_stations`, `courts`, and `prisons` reference tables are maintained manually until official integration is available.

## Data Classification

| Classification | Examples | Access |
|---|---|---|
| Public | Rights library content, general legal information | All users (unauthenticated) |
| Confidential | Case records, family contact details, lawyer profiles | Role-specific (RBAC) |
| Sensitive | Document contents, prisoner details, OCR extractions | Tightly restricted; encrypted at field level |
| Audit | Audit logs, human review records | Immutable; System Admin / Auditor read-only |
| Legal | Legal source texts, rule logic | Legal Reviewer manage; all backend read |

---

## Data Residency

**[PROPOSED — Requires GOV-APPROVAL]**
All data containing personal information of Indian citizens should be stored within India (data residency). Specific hosting requirements require government approval before production deployment.

---

## Synthetic Data Policy

Per PRD §21: All development and testing must use synthetic/composite data. No real FIR numbers, case numbers, prisoner names, or family contact details may be used in development or staging environments.
